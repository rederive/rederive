npm supply-chain protection: what happens when a package is sabotaged?

In January 2022 the maintainer of colors deliberately broke it: a new release, published with his own valid credentials, sent apps into an endless loop of garbage output. Nothing was hacked. Anyone who installed the update got it, because a package manager hands you whatever the publisher pushed.

With rederive, that kind of change gets caught before it ships. We rebuilt the relevant part of colors as a copy you own, then changed a single character in it. The check failed at once: two hidden tests broke, and the file's fingerprint no longer matched.

The real output, for the technically curious. @rederive/colors is a zero-dependency rebuild of strip() — the part of colors@1.4.0, the last release before the sabotage, that removes color codes. Here is the rdv checker on it, before and after we drop one character from the shipped JavaScript.

One dropped character, caught two ways at once: only 6 of 8 held-back tests pass, and the file's fingerprint (a hash of its exact bytes) no longer matches. In the output, "held-out" means the held-back tests and "frozen" means the examples the builders were shown. Don't trust the shipped file? The package carries its full spec and tests, so you can rebuild each language version yourself with sir-factory.

The tests even record the original's real limits: colors.strip removes only color codes, so cursor and title escape sequences survive it. rederive writes that down in the spec instead of hiding it.

Reduce your npm dependencies — by replacing them.

You chose a handful of dependencies. npm installed far more — code nobody on your team chose or read. Find out your own number — run this in any Node project:

# dependencies you chose vs. packages npm actually installed, and how many run install scripts
$ npx -p rederive rdv audit

You can't read them all

Nobody can. Scanners — npm audit and the good commercial ones — tell you which packages are known-bad today. The rest stay what they've always been: unread code with publish rights into your build.

So stop shipping them

rederive replaces a dependency with a verified, zero-dependency copy you own: rebuilt from its spec, checked on held-back tests, and fingerprinted in your tree. Your tree gets smaller; what remains is code you can answer for.

What it can replace today

  • Best fit: small, self-contained packages — string, number, date, URL, parsing and formatting helpers — including abandoned ones you can't get fixed upstream.
  • Packages that talk to the network or file system: JavaScript only today (their effects are checked by replaying recorded traffic).
  • Not yet: native add-ons and large frameworks.
  • Anything rederive can't verify is reported and left in place, never shipped unverified.
  • Every replacement keeps the original's license notice and records where it came from.

How rederive checks AI-written code

The same three steps apply whether the code replaces an npm package or is a new feature an AI wrote.

1 · A spec

Write down what the part must do

Each part gets a spec written in SIR (the spec format): a short, language-neutral description of its behavior, plus worked examples of inputs and expected outputs. One spec drives JavaScript, TypeScript and Rust.

2 · Held-back tests

Grade on examples the builders never saw

Some examples are kept as held-back tests, with expected answers that come from running the original package (or a reference you choose), not from whoever writes the replacement. Held back means hidden from the AI builders while they build. Afterwards the tests ship with the package, fingerprinted, so anyone can re-generate them from the original and confirm nothing changed.

3 · Independent builds

Several AI builds that can't see each other

Each part is built more than once, by AI builds that can't see each other's work. If independent builds disagree, the spec left room for guessing, so it gets tightened. Agreement isn't the test of correctness — the held-back tests, whose answers come from the original package, are.

After that, rdv check re-runs the held-back tests against the shipped code and compares fingerprints — free, offline, no AI — so it can run in your automated build pipeline (CI) on every change. Building uses your own AI model usage, on your machine. Each language is checked against the same tests, so the JavaScript, TypeScript and Rust versions can't quietly drift apart. The Claude Code plugin

Two commands inside Claude Code. The plugin adds three skills, so you can ask for the work in plain words.

> /plugin marketplace add rederive/rederive
> /plugin install rederive@rederive
sir-verify

Replaces a dependency. It writes the spec, records held-back tests by running the original, and runs the independent builds. Ask: "Get this project off decode-uri-component — re-derive it as a verified, zero-dependency copy in this repo."

preflight

For code with no tests. It records what the code does today as tests, then measures how strong those tests are by deliberately breaking the code and counting how often the tests notice.

greenfield-quorum

Builds a new feature part by part the same way, and brings the real design decisions to you instead of guessing.

Your team's existing AI-written code has no tests? Start with preflight. Using a different agent? The CLIs plus rederive.ai/prompt.md are the whole flow, written for any agent.

Questions

Can it replace an abandoned or unmaintained npm package?

Often, yes — if it's small and self-contained, like a string, date, URL or parsing helper. The replacement lives in your repo, so you don't need anyone upstream to publish a fix. If rederive can't verify a package, it says so and leaves it in place.

Aren't published tests leaked to the next model?

The tests are held back only while the AI builds the code. After that, their job is to let anyone re-check the result, so they ship with the package. A leaked test can't make wrong code pass, because the expected answers come from running the original package, not from the code being checked.

How is this different from Socket or Snyk?

Scanners like Socket and Snyk flag risky packages. rederive removes a package by replacing it with verified code you own. They answer different questions, so use both.

What does it cost?

The tools are free and open source. Building a replacement uses your own AI model usage, on your machine. Checking is free and offline, with no AI involved.

What about licenses?

Every replacement keeps the original package's license notice and records where it came from.

Does it work with Cursor or other agents?

Yes. The command-line tools and the setup prompt at rederive.ai/prompt.md work with any agent that can run shell commands. The plugin is for Claude Code.
