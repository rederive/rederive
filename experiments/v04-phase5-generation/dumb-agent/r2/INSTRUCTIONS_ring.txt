## SIR FORMAT (line-oriented; one directive per line, repeated lines allowed)

UNIT <name>
KIND FUNCTIONAL
FIDELITY spec
SIG <name>(arg1, arg2, gate) -> Promise<...>
DESCRIPTION <prose; repeat this line as many times as you need>
PAR <one line naming what runs concurrently>          # only for concurrent units
RING <one line naming how the token circulates>       # only for ring units
INVARIANT <one checkable property; repeat as needed>

A blind engineer will receive ONLY your SIR — no schema, no examples, no access
to any reference implementation, and no ability to ask you a question. Whatever
you leave unsaid, they will guess.

## CONCURRENCY KEYWORDS ARE HINTS — the contract lives in DESCRIPTION + INVARIANT

`PAR` and `RING` (and a declared timer/microtask or cancellable-resource effect) tell the VERIFIER which
mode to run. They tell the blind engineer almost nothing: unlike `TAKES` or `GIVES`, their semantics are
not inferable from their syntax. So never let a keyword carry meaning by itself — write the behavior out:

- **`PAR`** — say what makes the sub-traces independent, and pin the two things that look alike and aren't:
  *what the result is keyed by* (input position, not completion order) and *the concurrency bound* with the
  instant a unit counts as in flight.
- **`RING`** — say who takes the token, who passes to whom, and who releases it. State mutual exclusion
  (at most one holder ever) and no-loss (released exactly once, nobody holding at return) as INVARIANT
  lines. Both are invisible on the value channel: a unit with correct output can still duplicate or strand
  the token.
- **Empty input** deserves its own INVARIANT for both — it is the case where "do nothing" and "do the
  protocol zero times" differ observably.

**Name the collaboration boundary explicitly, and name it the RIGHT WAY ROUND.** Concurrency units are
handed a harness-owned object (a gate, a clock, a channel), and the split of labor between unit and
harness is the ambiguity these contracts fail on — in the v0.4 cleanroom trial, 2 of 3 blind emitters
read "each mapping is performed by awaiting `gate.open(value)`" as *the gate computes the mapping* and
returned the input unchanged. They were right to; the sentence permits it. Write which side computes,
and what the harness call resolves with.

**The default is not negotiable: the UNIT does the domain work; the harness collaborator only signals
timing.** `gate.open(v)` resolves with `v` unchanged and computes nothing; a clock decides when, never
what. Stating the boundary is not enough if you state it backwards — a weak model handed "return the
even integers, at most N in flight" wrote a flawless, unambiguous contract that defined the result as
"the elements the gate says are truthy", and three blind emitters implemented it identically and
returned *every* element. It converged. It respected the bound. It had thrown the requirement away.
**Quorum measures agreement, not fidelity**, so nothing downstream can catch this: if a requirement
names a computation, that computation is the unit's, and the SIR must say so.

Acceptance is unchanged and unforgiving: **a cold re-emitter builds it correctly from the SIR alone.**
Quorum divergence means the construct needed a footnote to be understood, which means it is specified
wrong. Harden the SIR; never add the footnote.


## Writing a `RING` unit (token-coordinated concurrency)

A ring is a single circulating permission: only the token-holder acts. The token
lives on the gate — `gate.token.take(who)`, `gate.token.pass(from, to)`,
`gate.token.release(who)` — so the verifier can watch it.

**A ring is a REFINEMENT.** Every ring run must be a run the unconstrained unit
could also produce: it may DROP outcomes, never INVENT one. If you are imposing a
ring on racy code (rather than recognizing one already there), say so in the SIR —
silently narrowing what a unit can do is how a contract lies politely.

**The token discipline is asymmetric — say it exactly.** There is ONE token, so
it is TAKEN exactly once, by the first actor. Every later actor RECEIVES it via
`pass(from, to)` and must never call `take()`. It is RELEASED exactly once, by
the last actor. Writing "the token is taken n times, once per actor" contradicts
mutual exclusion and is the single most common way this contract goes wrong: a
weak model wrote precisely that, and blind emitters split on whether later actors
also call `take()` — same values, same output, different protocol. Nothing on the
value channel can see that split, so the SIR has to settle it.

**`RING` is a HINT.** State these as `INVARIANT` lines:

- SAFETY — the outcome set is a subset of the unconstrained unit's
- PROTOCOL — one `take` by the first actor, `pass` for every handoff, one
  `release` by the last; name who does each
- LIVENESS, mutual exclusion — at most ONE holder at any instant
- LIVENESS, no loss — nobody holds the token when the unit returns

Those liveness properties are the only two ways a ring can break, and both are
invisible on the value channel: a unit with a lost or duplicated token still
returns the right answer.
